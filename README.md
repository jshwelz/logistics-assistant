# Faro Austral Logística

A document assistant for a fictional logistics company. Upload a PDF or DOCX, wait for processing, and ask questions. Answers cite the stored passage and its page. If the evidence is not enough, the answer says so.

The stack is FastAPI, React, Celery, Redis, PostgreSQL with pgvector, and OpenTelemetry with Jaeger.

## Run locally

Copy `.env.example` to `.env`. Leave the provider values empty to stay on the fake provider. For Gemini, set `EMBEDDING_PROVIDER=openai`, `ANSWER_PROVIDER=openai`, the model names, `PROVIDER_BASE_URL`, and `PROVIDER_API_KEY`. The name `openai` is the HTTP adapter, not the OpenAI service. Keep `.env` out of Git.

```bash
docker compose up --build
```

- Frontend: http://localhost:8080
- API: http://localhost:8000
- Jaeger: http://localhost:16686

Host ports can move without changing the addresses containers use:

```bash
API_PORT=8001 POSTGRES_PORT=5434 REDIS_PORT=6380 JAEGER_UI_PORT=16687 JAEGER_OTLP_PORT=4319 docker compose up --build
```

Compose starts the frontend, API, worker, database, Redis, and Jaeger. Migrations run first. The frontend calls the API through nginx at `/api`.

Uploads are limited to 20 MiB. Same bytes are deduplicated. A replacement becomes current only after it is ready. Details, including what is not implemented, are in `DECISIONS.md`.

## Tests

Fake providers only. No API key. The command starts Postgres and Redis, installs the locked dev dependencies, then runs Ruff and pytest. Pytest uses `logistics_test` and Redis DB 1.

```bash
./scripts/check.sh
```

GitHub Actions (`.github/workflows/ci.yml`) runs those same backend commands against pgvector and Redis, and runs `npm ci` plus `npm run build` for the frontend. Providers in CI are fake.

## Evaluation

Example documents are generated by `eval/corpus.py`. The worker mounts `eval/` at `/app/eval`. Results go to the separate database `logistics_eval`, derived from `DATABASE_URL`.

```bash
docker compose exec -T worker python eval/run_eval.py
docker compose exec -T -e EVAL_PROVIDER=configured worker python eval/run_eval.py
```

The first command is the fake provider. The second uses the provider configured for the worker. Hit rate counts whether the expected page and sentence are in the top 5 chunks. It is not answer accuracy.

Measured runs are in `eval/results/`. On 6 November 2026 the fake run retrieved 6/10 and the Gemini run retrieved 9/10. In that Gemini run, `q4` was retrieved and then abstained, and `q7` failed with `provider_malformed`. The later `q7` call, `eval/results/2026-11-06-q7-rerun.json`, finished `insufficient_evidence` with no citations. The expected sentence had been retrieved. That call is not an answer-accuracy success.

## Trace

`observability/ask-trace.json` is a complete question trace from the API through Celery and PostgreSQL to the Gemini call. `observability/README.md` says what it shows.

## Limitations

- No OCR. A scan with no text fails explicitly.
- Complex layouts may extract in the wrong order.
- Citation checks bind a claim to a stored chunk. They do not prove every sentence is supported.
- No authentication. This is a local demonstration.
- Recovery scheduling assumes one worker.
- Vectors are 768 dimensions. Migration `0003` removes older 64-dimension chunk rows.
